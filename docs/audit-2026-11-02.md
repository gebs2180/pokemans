# Audit, 2026-11-02

What would hurt once strangers from Discord use Rawmark: a pass across access control, concurrency, expiry, uploads and logging, where earlier reviews went feature by feature. Each finding was proved by a test before it was fixed. Nothing here touched prod.

## Result

**Strangers can't reach each other's data.** Every route refused every outsider, using real ids from a real sold card. Two buyers can't win one card, and the limits on photo size, photo type and photo links held.

**The harm is elsewhere:** 14 findings, all closed. Zach decided the last 5 the same day, so 13 are fixed, though finding 1 needs a step from him before it works, and finding 9 was settled by removing the unused email.

**Do this before the next tester:** add the email line to the Auth0 Action (finding 1). If the live Action matches `docs/auth.md`, neither side of a deal can see the other's email, and that's the only way they can reach each other.

## How this was tested

`./gradlew check` with `POKEMANS_REQUIRE_DOCKER=true` passes: 278 tests in the app module, none failed, and the Testcontainers tests ran. 18 of the 37 tests first run against the unfixed code failed. Five of those were a bug in my test setup and two were existing EasyPost tests changed to expect the new lookup, so they don't count as findings.

- `offers/RouteSweepTest` reads every route from Spring's own mapping, so a new route is covered automatically. It builds a real sold card, label and buyer, then attacks them as four kinds of outsider.
- `offers/MarketRacesTest` runs requests at the same instant on real threads against real Postgres.
- `intake/PhotoLimitsTest` runs against real MinIO.
- The proofs of findings 7 to 10 and 14 first ran as failing tests. They then moved into `offers/MarketRulesTest`, `intake/PhotoLimitsTest`, `intake/PhotoChecksAtOnceTest` and `identity/EndingAccessTest`, which pass.

**Checking the checks.** The sweep passed first time, which proves little on its own. So I removed the ownership checks from `requireDeal` and `withdraw` and ran it again. It failed on `/deals/{listingId}/received`. The checks were then restored. The test for finding 12 was written alongside its fix, so I also confirmed it fails without the fix.

**Not covered:** real Auth0, real EasyPost, R2, a real oversized request through Caddy, and the live server. Real Caddy 2.10 accepts the new config (`caddy validate`).

## Findings

### 1. Buyer and seller emails are probably empty on prod (High, needs Zach)

**Where:** `identity/CurrentUser.java` reads an `email` claim from the access token, once, on first login. The post-login Action in `docs/auth.md` set only the roles and MFA claims, and Auth0 access tokens carry no email unless an Action adds it.

**Harm:** the email on a deal is the only way the two sides reach each other, and both sets of terms promise it (clause 7). The buyer pays off the app, so with no email neither side can arrange payment. The screens just leave the email out, so nothing looks wrong.

**Why nobody saw it:** the e2e stack's mock login puts `email` in the access token (`e2e/stack/mock-oidc.mjs:36`). That's also what the UX review ran on, so its "the seller gets the buyer's email" doesn't describe prod.

**Evidence:** `identity/ContactEmailTest` failed with "expected sam@example.com but was null": a user first seen without an email stayed empty for good, whatever later tokens said. I read `docs/auth.md`, not the live tenant, so the Action there may differ.

**Fixed:** the stored email now follows the token, so users who already logged in get filled in on their next login. `docs/auth.md` has the new Action lines. They pass verified emails only, because the address is shown to strangers.

**Zach:**
1. Add those lines to the live Action. This is the step that makes the fix work.
2. Log in again and buy something in a test deal, to confirm the email shows.

I haven't confirmed that Auth0 accepts an unnamespaced `email` claim. If it refuses, use a namespaced claim and change `CurrentUser` to match.

### 2. A retry after a lost answer buys a second EasyPost label (High, fixed)

**Where:** `offers/EasyPostShippingProvider.java`, `buy`.

**Harm:** EasyPost sells the label, then the answer times out (or we crash before recording it). We record nothing, so the buyer's "try again" pays a second time. The first label is on our account, isn't billed to anyone, and can't be refunded from the admin page. The review of 2026-10-26 left this open.

**Evidence:** `EasyPostShippingProviderTest.aRetryAfterALostAnswerGetsTheLabelAlreadyBoughtNotASecondOne` failed: the code went straight to creating a shipment.

**Fix:** EasyPost's docs say a shipment can be retrieved by its reference, and ours is the listing id. So `buy` looks that up first and returns the label if one was bought. A 4xx means none exists, and the purchase goes ahead as before. A 5xx or timeout stops it, because we can't tell whether a label was bought, and the buyer can retry.

**Left:**
- This is tested against a mock built from EasyPost's docs. **Before real labels, run one purchase and one retry with the test key.**
- If that lookup answers 4xx for some other reason, we're back to today's behaviour, so it can't block labels.
- EasyPost says references aren't guaranteed unique. A first try that created a shipment but didn't buy, then a second that bought and lost its answer, could leave the lookup returning the unbought one. A retry then buys again. That needs two failures on one deal, and the reference still matches the pair in the dashboard.

### 3. Addresses in a provider's error reach the logs and Sentry (High, fixed)

**Where:** `offers/Shipping.java`, `buy`, which logged the whole exception at ERROR. The earlier fix kept this text from buyers on purpose and sent it to the log.

**Harm:** RestClient puts the response body in the exception's message, and EasyPost's address errors can quote the address. ERROR lines go to Sentry, a third party, and into server logs. The 502 also kept the exception as its cause.

**Evidence:** `MarketRacesTest.addressesInAProvidersErrorStayOutOfTheLogs` failed with the address in the captured output.

**Fix:** the log gets the listing id and the status code or exception type, never the text, and the cause is dropped. The cost is that diagnosing a failure now means opening the EasyPost dashboard.

**Left:** a failed refund still stores the provider's text in `label_refund`. Only the admin sees it, and it never reaches the log.

### 4. A finished deal can still buy a label, billed to the buyer (Medium, fixed)

**Where:** `offers/ListingService.java`, `buyLabel`, which checked only for a cancelled deal.

**Harm:** a label fails, the card ships another way, and the admin records the arrival by hand. A retry from either side then buys a label for a card that has already arrived, and it appears on the buyer's monthly bill.

**Evidence:** `MarketRacesTest.aFinishedDealGetsNoLabel` got 200, not 409.

**Fix:** with no label yet and an outcome recorded, the purchase gets a 409.

### 5. A double click on Buy tells the winner they lost (Medium, fixed)

**Where:** `offers/ListingService.java`, `accept`.

**Harm:** the card and label were always safe. But a second accept from the same buyer, by double click or by retrying after a dropped connection on a phone, got 409 "Another buyer took this card first". The buyer believes they lost a card they're committed to pay for, and may buy elsewhere. The seller ships anyway.

**Evidence:** `aSecondAcceptByTheSameBuyerGetsTheirDealNotAnotherBuyersRefusal` got 409. `aDoubleClickOnAcceptBuysOneCardAndOneLabel` got `[409, 200]`.

**Fix:** `accept` takes the card's listing lock, the one posting, voiding and cancelling already use, and returns the deal to the buyer who already holds it. Another buyer still gets 409.

### 6. Nothing limits the size of a request to the API (Medium, fixed)

**Where:** `deploy/Caddyfile`.

**Harm:** anyone who can sign in can reach a route that parses JSON, even with no org, because the body is read before any org check. One very large string can exhaust the heap, and the image runs with `-XX:+ExitOnOutOfMemoryError`, so the API restarts. I didn't run this attack; it follows from the configuration.

**Evidence:** `DeployConfigTest.theApiTakesNoHugeBodies` failed.

**Fix:** a 1 MB limit on `/api/*`. Photos go straight to storage, so nothing legitimate comes close. It takes effect on the next deploy of Caddy.

### 7. Nothing limits uploads, and photo checks can exhaust the server (Medium, fixed)

**Where:** `intake/PhotoService.java`. There are no rate limits anywhere: not in the app, and not in stock Caddy.

**Harm, storage:** one seller can request 300 upload slots on one card, and every slot takes 25 MB. That's 7.5 GB in about a minute, and nothing stops a second card. Testers are invited, so this needs a bad actor or a broken client.

**Harm, memory:** `confirm` reads the whole file and decodes it inside a database transaction. A 48 MP phone photo needs about 150 MB to decode. The API container has 1,536 MB, and 60% of that is heap. So a few sellers uploading at once could get it killed, and ordinary phones are enough. It also holds a database connection throughout, so a burst can stall other requests. This part is reasoned from the numbers, not reproduced.

**Evidence:** a test got 300 of 300 slots.

**Fix:** Zach left the numbers to me: 50 upload attempts per card, 200 per org in 24 hours (`pokemans.storage.max-photos-per-card`, `max-photos-per-org-per-day`), and 2 photo checks at a time (`photo-checks-at-once`). A photo waits its turn outside the transaction, so waiting holds no database connection, and after 60 seconds the seller is asked to try again. The decode itself stayed in the transaction: with only 2 running, that's no longer a risk.

200 a day is about 65 cards at three photos each, so a seller with a big binder finishes the next day. Raise it if that gets in anyone's way.

### 8. Nobody can be removed, and an invite can't be revoked (Medium, fixed)

**Where:** `identity/AdminOrgController.java` offers create, list and invite only. The route sweep lists no way to end a membership, revoke an invite or suspend an org.

**Harm:** both sets of terms say breaking them can end someone's part in the test, and the app can't do that. A link posted in the wrong channel stays good until someone uses it or it expires after 7 days.

**For now:** block the user in Auth0. Their access token keeps working until it expires. A leaked invite has no workaround except accepting it yourself.

**Fix:** "People and links" on the admin page lists an org's members and open invite links, and can remove a member (with a reason) or revoke a link. Nothing is deleted: the row records who, when and why. Membership is read on every request, so someone removed loses the org at once. They can be invited back. Their org's listings and deals stay: void those separately if they should go too.

### 9. An invite for one email works for anyone holding the link (Medium, settled)

**Where:** `identity/InviteService.java`, `accept`, which never reads the invite's email.

**Evidence:** a test got 200.

**Settled:** Zach chose not to bind (2026-11-02). Binding would lock out anyone who signs in with a different address. Whoever holds the link can use it, and revoking (finding 8) deals with a leaked one. The admin page never sent an email, so the field and its column are gone.

### 10. A card found doubtful stays on the market (Medium, fixed)

**Where:** `offers/ListingService.java`. `OfferService.quote` refuses a doubted card an offer, but nothing checks again once it's posted.

**Harm:** the admin records "suspected counterfeit" on a posted card, and a buyer can still take it. Today the admin has to remember to void the offer as well.

**Evidence:** a test found the listing still on the market.

**Fix:** recording a doubt now voids the card's live offers and takes any listing down, in the same transaction and under the card's listing lock, so it can't race a buyer. A card a buyer already took stays a deal, and the admin decides whether to cancel it. A later "verified" needs a new offer.

### 11. A cancelled deal still shows the seller the label, with the buyer's address (Low, fixed)

**Where:** `offers/ListingService.java`, `listingView`.

**Harm:** after we cancel, the seller can still print a label that's paid for on our account and may be refunded, and it shows the buyer's address.

**Evidence:** `aCancelledDealStopsShowingTheSellerTheLabel` found the URL.

**Fix:** the printable link goes once a deal is cancelled. The tracking stays. The API already allowed a null link and the screen already handles one.

**Left:** a seller who saved the PDF still has it, and EasyPost's link stays live. Buyer terms clause 7 names name and email only, yet the seller sees the buyer's address on any label. That's unavoidable, but the terms could say so.

### 12. Buyers see the seller's private label for the card (Low, fixed)

**Where:** `offers/ListingService.java`, `market` and `deals`.

**Harm:** the label is free text a seller types for themselves, and it was sent to every buyer before any sale. It can hold a name or a phone number. No buyer screen shows it, but it was in the API response.

**Evidence:** with the fix removed, `buyersDontGetTheSellersOwnLabelForTheCard` returned "Call Sam 555-0100".

**Fix:** buyers get the card without it. The admin's views keep it.

### 13. Invite tokens reach the access log (Low, fixed)

**Where:** `deploy/Caddyfile`. The token is in the path, and a link stays usable for a week.

**Evidence:** `DeployConfigTest.inviteTokensStayOutOfTheAccessLog` failed.

**Fix:** a log filter replaces the token. Real Caddy accepts the config, but I didn't watch a real request go through it.

### 14. A login in both a seller org and a buyer org can buy its own card (Low, fixed)

**Where:** `offers/ListingService.java`, `accept`.

**Harm:** it would put a fake sale in the track record and a label on our account. Only a person invited to both sides can do it.

**Evidence:** a test got 200.

**Fix:** a buyer org that shares a member with the seller's org gets a 409, whoever in it clicks. Testing both sides now takes two logins.

## Checked and sound

**Org isolation.** Tested by `RouteSweepTest`:
- Every `/api/orgs/{orgId}/**` route answered 404 to a member of another seller org, a member of another buyer org, and a signed-in user with no org, for both the seller's and the buyer's org. Nothing was written.
- With the attacker's own org and the victim's ids, every route was refused. The one exception is the market: a buyer who tries a taken listing gets 409, and no more.
- Sellers can't reach buyer routes, and buyers can't reach seller routes.
- Every route is under `/api/admin/`, is org-scoped, or is one of three on a short list (`/api/me` and the two invite routes). A new route outside these fails the test.

**Roles.** Every `/api/admin/**` route answers 403 to a seller and a buyer. `CrossOrgAccessTest` already covers a token that claims ADMIN without MFA. Only an admin can record custody as checked.

**Concurrency.** Tested with simultaneous requests against real Postgres:
- Four buyers racing for one card, three rounds: one 200, three 409s, one deal, one label, and the losers have nothing.
- A buyer racing a withdraw, and a buyer racing a void: one outcome each time.
- Double clicks on post, void, cancel and recording an arrival: each counts once.

**Expiry.** A listing is open one microsecond before `expires_at` and expired at it, and the market's query agrees with the status on both sides. An expired listing can't be taken or withdrawn, and an expired offer can't be posted.

**Uploads.** Tested against MinIO:
- Size and type are refused at the slot.
- A longer file or a different content type is refused by storage, because the signature covers them.
- Files that aren't photos, whatever they claim, never pass.

**Photo links.** The bucket is private. A photo's address with no signature gets nothing, and a crop's signature doesn't open the original beside it. The address does contain the seller's org id, which gets a stranger nothing (see org isolation). Links last 15 minutes and work for anyone who has one.

**Secrets.** Every provider key goes in a header, never a URL, and each config record hides its key when printed. SQL logging is off. Sentry gets no request bodies, headers or IPs.

**Addresses and emails.** Apart from findings 3 and 13, no log line in the code includes an address, email or token. Buyers never get the printable label, and the seller's email reaches a buyer only after a sale.

## Noticed, not findings

- `/api/orgs/{orgId}/cards/{cardId}/identification` returns the card reader's raw error text and the reviewer's id to the seller. It's harmless today, but it isn't meant for them.
- An offer's `expired` flag turns true on a listing still open, since offers last 7 days and listings 14. The market doesn't use that flag, so a buyer can take a posted price up to 21 days after it was set. That's what the rules say, but it's worth knowing when prices move.
